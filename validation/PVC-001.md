# PVC-001 — PALACO Validation & Certification Standard

**Status:** DRAFT candidate  
**Scope:** PALACO Core Alpha  
**Authority:** This document defines validation semantics. It does not itself authorize execution, merge, deployment, or release.

## 1. Purpose

PVC-001 defines the normative G0–G9 validation chain for PALACO Core Alpha. Each gate records Requirements, Validation Method, Evidence and Result.

A successful validation result establishes only the claim explicitly tested by that gate.

`VALIDATION PASS ≠ AUTHORITY ≠ EXECUTION AUTHORIZATION ≠ RELEASE AUTHORIZATION`

## 2. Normative result states

- **PASS** — every mandatory requirement for the gate is supported by current, attributable evidence.
- **FAIL** — one or more mandatory requirements are demonstrably violated.
- **HOLD** — evaluation cannot validly continue because a prerequisite, authority, artifact, environment or required evidence is absent or blocked.
- **INCONCLUSIVE** — evidence exists but is insufficient, conflicting, stale, unverifiable or does not support a determinate PASS/FAIL conclusion.

Decision order: a demonstrated mandatory violation is FAIL; an absent mandatory prerequisite, required artifact, authorization or evidence is HOLD; present but conflicting, stale or unverifiable evidence is INCONCLUSIVE; PASS requires all mandatory requirements to be supported by current attributable evidence. Where multiple problems coexist, record all findings and retain the blocking outcome; never promote an uncertain state to PASS.

Unknown, missing, stale or conflicting evidence MUST NOT be silently converted to PASS.

### 2.1 Initial G0–G9 automation

`pvc_validate.py` evaluates repository identity, the Cargo workspace inventory and
revision binding for G0. For G1 it validates the SystemGraph structure, declared
required nodes and relations, endpoint references, relation-kind semantics and
source revision. For G2 it derives the local Cargo workspace dependency graph,
checks references and cycles, and validates explicit startup/shutdown ordering
constraints. Cargo edges include normal, build and dev dependencies; the derived
graph digest and a digest over both ordering lists and recorded approval
metadata bind the ordering evidence.
For G3 it checks an ExecutionPlan against the exact SystemGraph digest, requires
one plan step for every service, checks dependency edges against explicitly
declared relation kinds, rejects cycles and authority-shaped extra fields, and
generates a deterministic set of parallel execution layers. Every step must
identify a recovery point. The formats are defined in
`system-graph.schema.json` and `execution-plan.schema.json`;
`core-alpha-scope.json` is the versioned scope and inventory input.
Approval identities and decision references are recorded claims; these local
digests detect mismatches but do not authenticate a reviewer or grant authority.
Human review remains necessary for any governance or release decision.

The validator emits JSON and Markdown evidence containing the source revision,
validator version, input digests, dependency graph, execution schedule and gate
findings. CI uploads these files as the `pvc-001-evidence` artifact. A gate
result of HOLD or INCONCLUSIVE is reported without granting authority;
demonstrated validation failures fail the CI step.

The initial scope file intentionally does not invent an approved graph inventory,
and no SystemGraph artifact is checked in yet. G1 requires the required node and
relation inventory plus an approval record binding the graph revision, approver
and decision reference. Therefore G1 remains HOLD until those requirements and
a graph bound to the evaluated revision are supplied. G2 checks the current Cargo
dependency graph, but remains HOLD until startup/shutdown constraints are
explicitly recorded and approved against that graph's digest.
G3 remains HOLD until G1 and G2 pass and a revision-bound ExecutionPlan is
provided. An ExecutionPlan is a deterministic proposal only: it does not create
authority or authorize execution.
For G4 the evidence generator runs the `palaco-runtime` and `palaco-kernel`
Cargo test suites, records the command, exit code, output digest, and results
for the required execution, escalation, and safe-state scenarios, bound to the
source revision, clean-tree state and CI run when available. G4 is FAIL
when the test command or a required scenario fails; it is HOLD if test evidence
is unavailable, required scenarios are missing, or G3 is not PASS. A G4 PASS
also requires a clean source tree and therefore demonstrates the selected
runtime/kernel contracts against a validated G3 input, not authorization to
execute the proposed plan.
For G5 the evidence generator runs the `palaco-eventbus`, `palaco-rio-core`
and `palaco-observatory` test suites. It records the command, exit code,
output digest, source revision, clean-tree state and required event lifecycle,
provenance, observation and authorization-separation scenario results. G5 is
FAIL when the command or any required scenario fails; it is HOLD when evidence
is missing or G4 is not PASS, and INCONCLUSIVE for a dirty or unverifiable
source tree. The eventbus contract only publishes events: it exposes no
authorization or governance operation. Passing these tests does not grant
authority.
For G6 the validator builds an implementation inventory from Cargo workspace
metadata and compares every SystemGraph `source_paths` entry with the checkout.
It reports a versioned ruleset, inventory and graph digests, source revisions,
and per-rule classifications. Existing graph paths must cover every workspace
package; missing paths or uncovered packages are mandatory violations (FAIL).
G6 is HOLD when the graph, inventory, or any G0–G5 PASS prerequisite is absent,
and INCONCLUSIVE when graph and implementation revisions differ. This is a
source-path/workspace-coverage check; it does not claim semantic equivalence
beyond those explicit rules.
For G7 the validator runs `cargo test --locked --workspace`, captures the
integrated output digest and verifies the G4/G5 runtime, event, provenance,
observability and authorization-boundary scenarios in that run. It reconciles
the ordered G0–G6 results, repository and scope-manifest digest, source
revision and clean-tree state, SystemGraph artifact digest, dependency/plan
digests, implementation inventory digest, and shared CI run ID.
A failed integration test or prior mandatory FAIL remains FAIL; absent prior
PASS results or required test evidence holds G7, while conflicting revisions,
artifacts or run IDs are INCONCLUSIVE. G7 PASS is an integration finding only;
it does not authorize execution or release.
For G8 the validator checks the Core Alpha security checklist and threat-model
artifact, runs `cargo audit --locked` when its tool is available, verifies
digests for evidence referenced by PASS controls, and records the presence of
dependency-audit tooling/configuration and a dedicated security workflow.
Missing checklist/control evidence is HOLD; malformed
checklists or digest mismatches are FAIL; stale or unbound evidence is
INCONCLUSIVE. An OPEN threat model or any unresolved control prevents PASS.
The checked-in checklist deliberately remains OPEN because the threat-model
draft says production is blocked and supply-chain, secrets/configuration,
adversarial and independent-review evidence is not yet approved.
For G9 the validator requires a structured `validation/release_validation.md`
table binding the exact source revision, release artifact, prior G0–G8 JSON
report, attestation and recorded decision. Each artifact reference uses
`repository/relative/path@sha256`; the validator computes and checks every
digest, verifies that the referenced report is for the same revision and that
its ordered G0–G8 results are all PASS, and reconciles them with the current
gate results. The attestation JSON must bind that exact source revision,
release-artifact digest and evidence-report digest. Missing evidence is HOLD,
digest/format violations are FAIL, stale revision bindings are INCONCLUSIVE,
and prior blockers remain blockers.
G9 reports technical release eligibility separately from an APPROVE claim.
The recorded authority and decision are not authenticated; a G9 PASS does not
grant release authority or trigger merge/deployment.

## 3. Evidence minimum

Every gate decision MUST identify, where applicable:

- repository and relevant path(s);
- source commit / immutable revision;
- validation method and validator version;
- runtime/toolchain/environment identity when execution evidence is claimed;
- run/job/test identifiers;
- relevant artifact, log or evidence digests when available;
- timestamp;
- reviewer/decision identity where a human decision is required;
- result and reason.

Evidence from one revision MUST NOT silently certify another revision.

## 4. G0–G9

### G0 — Scope & Identity

**Requirements**
- Core Alpha scope and repository are unambiguous.
- evaluated source revision is identified.
- required components and exclusions are declared.

**Validation Method**
- repository/scope inspection;
- revision binding;
- declared component inventory comparison.

**Evidence**
- repository identity;
- commit SHA;
- component/scope inventory.

**Result**
PASS only when the validation subject is uniquely bound.

### G1 — SystemGraph Completeness

**Requirements**
- required Core Alpha services, capabilities, resources, lifecycle and events are represented;
- required relations are explicit;
- unresolved mandatory references are absent.

**Validation Method**
- SystemGraph schema validation;
- graph completeness and reference checks.

**Evidence**
- SystemGraph artifact and digest/revision;
- validator output;
- declared RelationKind semantics.

**Result**
PASS only for the exact validated graph.

### G2 — Structural & Dependency Validity

**Requirements**
- dependency relations are valid;
- prohibited cycles are rejected;
- startup/shutdown ordering constraints are representable.

**Validation Method**
- dependency analysis;
- cycle/ordering tests;
- negative fixtures.

**Evidence**
- validator/test results;
- failing fixtures for prohibited structures.

**Result**
PASS only when required dependency, cycle and ordering checks succeed on the identified graph and negative fixtures reject prohibited structures.

### G3 — Planner & ExecutionPlan Conformance

**Requirements**
- Planner consumes a validated SystemGraph;
- output is deterministic for equal governed inputs/version;
- dependency ordering, safe parallelism and recovery/rollback points are explicit;
- plan does not create authority.

**Validation Method**
- deterministic plan tests;
- ordering/cycle/recovery tests;
- interface review.

**Evidence**
- Planner revision;
- example Core Alpha ExecutionPlan;
- test/run evidence.

**Result**
PASS does not authorize execution.

### G4 — Kernel / Runtime Orchestration

**Requirements**
- Kernel consumes the governed runtime/execution plan through defined interfaces;
- startup/shutdown dispositions fail closed;
- revalidation boundaries are preserved.

**Validation Method**
- contract tests;
- startup/shutdown scenarios;
- safe-state/escalation negative tests.

**Evidence**
- kernel/runtime source revision;
- scenario/test results.

**Result**
PASS only when the identified kernel/runtime revision satisfies governed-plan, fail-closed and revalidation scenarios, including negative cases. This does not authorize runtime execution.

### G5 — Event & Observability Integrity

**Requirements**
- Core Alpha eventbus interface is explicit;
- required lifecycle/events are traceable;
- observability cannot create authority.

**Validation Method**
- interface and event-contract tests;
- traceability checks;
- negative authority-escalation tests.

**Evidence**
- eventbus contract;
- event/trace fixtures;
- test results.

**Result**
PASS only when required lifecycle events are traceable and negative tests demonstrate that observability cannot grant authority.

### G6 — Architecture Compliance

**Requirements**
- implementation is compared against the validated SystemGraph;
- deviations are classified and reported;
- mandatory violations prevent PASS.

**Validation Method**
- Architecture Compliance Engine;
- implementation inventory;
- negative fixtures.

**Evidence**
- Markdown/JSON compliance report;
- rule-set version;
- implementation and SystemGraph revisions.

**Result**
PASS only for the identified implementation and SystemGraph revisions when mandatory compliance rules have no unresolved violations.

### G7 — Integrated Core Alpha Validation

**Requirements**
- G0–G6 required outputs are mutually compatible;
- integration scenarios preserve fail-closed semantics;
- unresolved mandatory findings are absent.

**Validation Method**
- integrated validation suite;
- cross-component contract checks;
- evidence reconciliation.

**Evidence**
- integrated run IDs;
- exact component revisions;
- consolidated evidence record.

**Result**
PASS only when the required G0–G6 outputs reconcile for the same declared integration scope and mandatory integration and fail-closed scenarios succeed.

### G8 — Security Validation

**Requirements**
- Core Alpha threat model exists;
- mandatory security controls are defined and tested;
- dependency/supply-chain, secrets/configuration and relevant adversarial checks are evaluated;
- security-critical unknowns are not treated as satisfied.

**Validation Method**
- threat-model review;
- configuration/dependency inspection;
- negative/adversarial tests;
- security checklist.

**Evidence**
- `validation/security_checklist.md` when available and version-bound (otherwise required evidence is missing and the gate is HOLD);
- configuration/test evidence;
- relevant logs, run IDs and digests.

**Result**
Missing mandatory security evidence results in HOLD/FAIL as applicable, never implicit PASS.

### G9 — Release Validation

**Requirements**
- required G0–G8 decisions and evidence are complete for the exact release candidate;
- release artifact is bound to source/governance/evidence;
- decision authority is explicit;
- release decision is recorded.

**Validation Method**
- release checklist;
- evidence completeness review;
- artifact/source binding verification;
- authorized decision review.

**Evidence**
- `validation/release_validation.md` when available and version-bound (otherwise required evidence is missing and the gate is HOLD);
- exact source SHA;
- artifact digest;
- applicable certification/attestation;
- decision record and decision authority.

The checklist is a two-column Markdown table with `Field` and `Value` columns.
Required fields are `source_revision`, `artifact`, `evidence_report`,
`attestation`, `decision_authority`, `decision_record` and `decision`.
The three artifact values use `repository/relative/path@sha256`. The referenced
attestation JSON contains `source_revision`, `artifact_sha256` and
`evidence_report_sha256`, each matching the corresponding checklist-bound
evidence. `decision` must be `APPROVE` or `REJECT`; the identity and record are
claims and are not cryptographically authenticated by this validator.

**Result**
A complete, current G0–G8 evidence chain and artifact/source binding may establish `RELEASE_ELIGIBLE`; this is a technical finding, not approval. The recorded decision is reported separately as an unauthenticated claim; only a competent human authority can approve the exact release candidate. Neither state automatically merges, deploys or activates software.

`CI PASS ≠ G9 PASS`  
`G9 PASS ≠ AUTOMATIC MERGE`  
`G9 PASS ≠ AUTOMATIC DEPLOYMENT`

## 5. Gate ordering

`G0 → G1 → G2 → G3 → G4 → G5 → G6 → G7 → G8 → G9`

A later gate MUST NOT repair or silently override an earlier FAIL/HOLD. Re-evaluation requires new attributable evidence.

## 6. Evidence matrix

| Gate | Primary subject | Minimum evidence | Missing mandatory evidence |
|---|---|---|---|
| G0 | Scope/identity | repo + revision + inventory | HOLD |
| G1 | SystemGraph | graph + validator output | HOLD |
| G2 | Dependencies | analysis + negative tests | HOLD |
| G3 | Planner | plan + deterministic tests | HOLD |
| G4 | Kernel/runtime | contract/scenario tests | HOLD |
| G5 | Eventbus/observability | contract + trace tests | HOLD |
| G6 | Architecture compliance | versioned compliance report | HOLD |
| G7 | Integration | integrated run + reconciliation | HOLD |
| G8 | Security | threat model + security evidence | HOLD/FAIL |
| G9 | Release candidate | G0–G8 + artifact/source binding + recorded decision | HOLD |

## 7. Constitutional locks

- SystemGraph validity ≠ authority.
- ExecutionPlan ≠ authorization.
- Observability ≠ authority.
- Compliance PASS ≠ runtime authorization.
- CI PASS ≠ runtime authorization.
- Certification ≠ authority.
- Release eligibility ≠ automatic release.
- No mandatory evidence = no PASS.
- No authorized G9 decision = no release approval.
