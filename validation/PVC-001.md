# PVC-001 — PALACO Validation & Certification Standard

**Status:** DRAFT candidate  
**Scope:** PALACO Core Alpha  
**Authority:** This document defines validation semantics. It does not itself authorize execution, merge, deployment, or release.

## 1. Purpose

PVC-001 defines the normative G0–G9 validation chain for PALACO Core Alpha. Each gate records Requirements, Validation Method, Evidence and Result.

A successful validation result establishes only the claim explicitly tested by that gate.

`VALIDATION PASS ≠ AUTHORITY ≠ EXECUTION AUTHORIZATION ≠ RELEASE AUTHORIZATION`

## 2. Normative result states

- **PASS** — every mandatory requirement for the gate is supported by current, attributable evidence.
- **FAIL** — one or more mandatory requirements are demonstrably violated.
- **HOLD** — evaluation cannot validly continue because a prerequisite, authority, artifact, environment or required evidence is absent or blocked.
- **INCONCLUSIVE** — evidence exists but is insufficient, conflicting, stale, unverifiable or does not support a determinate PASS/FAIL conclusion.

Unknown, missing, stale or conflicting evidence MUST NOT be silently converted to PASS.

## 3. Evidence minimum

Every gate decision MUST identify, where applicable:

- repository and relevant path(s);
- source commit / immutable revision;
- validation method and validator version;
- runtime/toolchain/environment identity when execution evidence is claimed;
- run/job/test identifiers;
- relevant artifact, log or evidence digests when available;
- timestamp;
- reviewer/decision identity where a human decision is required;
- result and reason.

Evidence from one revision MUST NOT silently certify another revision.

## 4. G0–G9

### G0 — Scope & Identity

**Requirements**
- Core Alpha scope and repository are unambiguous.
- evaluated source revision is identified.
- required components and exclusions are declared.

**Validation Method**
- repository/scope inspection;
- revision binding;
- declared component inventory comparison.

**Evidence**
- repository identity;
- commit SHA;
- component/scope inventory.

**Result**
PASS only when the validation subject is uniquely bound.

### G1 — SystemGraph Completeness

**Requirements**
- required Core Alpha services, capabilities, resources, lifecycle and events are represented;
- required relations are explicit;
- unresolved mandatory references are absent.

**Validation Method**
- SystemGraph schema validation;
- graph completeness and reference checks.

**Evidence**
- SystemGraph artifact and digest/revision;
- validator output;
- declared RelationKind semantics.

**Result**
PASS only for the exact validated graph.

### G2 — Structural & Dependency Validity

**Requirements**
- dependency relations are valid;
- prohibited cycles are rejected;
- startup/shutdown ordering constraints are representable.

**Validation Method**
- dependency analysis;
- cycle/ordering tests;
- negative fixtures.

**Evidence**
- validator/test results;
- failing fixtures for prohibited structures.

### G3 — Planner & ExecutionPlan Conformance

**Requirements**
- Planner consumes a validated SystemGraph;
- output is deterministic for equal governed inputs/version;
- dependency ordering, safe parallelism and recovery/rollback points are explicit;
- plan does not create authority.

**Validation Method**
- deterministic plan tests;
- ordering/cycle/recovery tests;
- interface review.

**Evidence**
- Planner revision;
- example Core Alpha ExecutionPlan;
- test/run evidence.

**Result**
PASS does not authorize execution.

### G4 — Kernel / Runtime Orchestration

**Requirements**
- Kernel consumes the governed runtime/execution plan through defined interfaces;
- startup/shutdown dispositions fail closed;
- revalidation boundaries are preserved.

**Validation Method**
- contract tests;
- startup/shutdown scenarios;
- safe-state/escalation negative tests.

**Evidence**
- kernel/runtime source revision;
- scenario/test results.

### G5 — Event & Observability Integrity

**Requirements**
- Core Alpha eventbus interface is explicit;
- required lifecycle/events are traceable;
- observability cannot create authority.

**Validation Method**
- interface and event-contract tests;
- traceability checks;
- negative authority-escalation tests.

**Evidence**
- eventbus contract;
- event/trace fixtures;
- test results.

### G6 — Architecture Compliance

**Requirements**
- implementation is compared against the validated SystemGraph;
- deviations are classified and reported;
- mandatory violations prevent PASS.

**Validation Method**
- Architecture Compliance Engine;
- implementation inventory;
- negative fixtures.

**Evidence**
- Markdown/JSON compliance report;
- rule-set version;
- implementation and SystemGraph revisions.

### G7 — Integrated Core Alpha Validation

**Requirements**
- G0–G6 required outputs are mutually compatible;
- integration scenarios preserve fail-closed semantics;
- unresolved mandatory findings are absent.

**Validation Method**
- integrated validation suite;
- cross-component contract checks;
- evidence reconciliation.

**Evidence**
- integrated run IDs;
- exact component revisions;
- consolidated evidence record.

### G8 — Security Validation

**Requirements**
- Core Alpha threat model exists;
- mandatory security controls are defined and tested;
- dependency/supply-chain, secrets/configuration and relevant adversarial checks are evaluated;
- security-critical unknowns are not treated as satisfied.

**Validation Method**
- threat-model review;
- configuration/dependency inspection;
- negative/adversarial tests;
- security checklist.

**Evidence**
- `validation/security_checklist.md`;
- configuration/test evidence;
- relevant logs, run IDs and digests.

**Result**
Missing mandatory security evidence results in HOLD/FAIL as applicable, never implicit PASS.

### G9 — Release Validation

**Requirements**
- required G0–G8 decisions and evidence are complete for the exact release candidate;
- release artifact is bound to source/governance/evidence;
- decision authority is explicit;
- release decision is recorded.

**Validation Method**
- release checklist;
- evidence completeness review;
- artifact/source binding verification;
- authorized decision review.

**Evidence**
- `validation/release_validation.md`;
- exact source SHA;
- artifact digest;
- applicable certification/attestation;
- decision record and decision authority.

**Result**
G9 PASS establishes release eligibility/approval only as explicitly defined by the authorized decision.

`CI PASS ≠ G9 PASS`  
`G9 PASS ≠ AUTOMATIC MERGE`  
`G9 PASS ≠ AUTOMATIC DEPLOYMENT`

## 5. Gate ordering

`G0 → G1 → G2 → G3 → G4 → G5 → G6 → G7 → G8 → G9`

A later gate MUST NOT repair or silently override an earlier FAIL/HOLD. Re-evaluation requires new attributable evidence.

## 6. Evidence matrix

| Gate | Primary subject | Minimum evidence | Missing mandatory evidence |
|---|---|---|---|
| G0 | Scope/identity | repo + revision + inventory | HOLD |
| G1 | SystemGraph | graph + validator output | HOLD |
| G2 | Dependencies | analysis + negative tests | HOLD |
| G3 | Planner | plan + deterministic tests | HOLD |
| G4 | Kernel/runtime | contract/scenario tests | HOLD |
| G5 | Eventbus/observability | contract + trace tests | HOLD |
| G6 | Architecture compliance | versioned compliance report | HOLD |
| G7 | Integration | integrated run + reconciliation | HOLD |
| G8 | Security | threat model + security evidence | HOLD/FAIL |
| G9 | Release candidate | G0–G8 + artifact/source binding + authorized decision | HOLD |

## 7. Constitutional locks

- SystemGraph validity ≠ authority.
- ExecutionPlan ≠ authorization.
- Observability ≠ authority.
- Compliance PASS ≠ runtime authorization.
- CI PASS ≠ runtime authorization.
- Certification ≠ authority.
- Release eligibility ≠ automatic release.
- No mandatory evidence = no PASS.
- No authorized G9 decision = no release approval.
