# ORCH-056 — Signed checkpoint anchor evidence

DERIVED non-authorizing implementation on ORCH-055. Receipt transport carries registry ID, exact ORCH-052 checkpoint, signer key ID and raw 64-byte signature. SHA-256 signing digest: domain PALACO-ORCH-056-SIGNED-CHECKPOINT-ANCHOR-v1 followed by registry ID (32 bytes), checkpoint commitment (32 bytes), signer key ID (32 bytes). The existing strict Ed25519 verifier verifies this digest. Checkpoint integrity is recomputed before signature verification. Nonzero expected registry identity and revision are required.

Policy supplies expected registry ID, pinned public key, minimum revision and minimum epoch separately. Verification rejects identity mismatch, malformed checkpoint, either floor rollback and wrong key/signature. Returned SignatureCheckedAnchor has private fields and exposes comparison only; no export as a trusted ExternalAnchor or authorization token. assess_stored_checkpoint authenticates receipt evidence before bounded file inspection. Existing lower-level APIs remain available; this does not globally enforce use of the new path.

Eight tests cover exact signature plus rollback/fork comparison, identity substitution, altered statement, wrong signer/key reference, both floors, malformed commitment, an explicit restored-policy limitation and stored checkpoint integration. Test keys are fixtures; no real private keys or issued anchors are introduced.

Boundary: externally supplied policy is not authenticated by this module. Signing-key eligibility, revocation, governance, provisioning, registry/path mapping, a durable monotonic floor backend and trusted time remain outside scope. If pinned policy and floors are rolled back together, a still-valid old signature may be accepted; a negative-limit test preserves this fact. SignatureChecked means signature bytes verified under supplied policy, not freshness, grant, current authority, or execution approval. No network, filesystem mutation in review, replay reservation, activation or durable policy update.

AI-review through three lenses: TRIAS — comparison remains non-executing and cannot bypass existing grants; ORACLE — actual strict signature verification binds identity and checkpoint but cannot establish supplied policy origin or latest state; MENTOR — opaque checked evidence and one stored-candidate review path make misuse harder while keeping failure types explicit. Dissent: production anti-rollback stays HOLD until an independently governed monotonic policy store and key lifecycle are implemented and reviewed.

Next transition: define and test a durable independently provisioned policy/floor source with restart and rollback resistance, and feed that source into this verifier. Human independent review and GO-13 remain necessary before merge/activation. Exact-head CI evidence is recorded in the PR.
