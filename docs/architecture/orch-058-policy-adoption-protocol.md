# ORCH-058 — Staged policy adoption protocol

DERIVED non-executing orchestration implementation on corrected ORCH-057. PolicyPinBackend defines an independently authenticated, durable, linearizable compare-and-exchange store scoped to one governed registry. It must be rollback resistant outside the policy files' failure domain. UnavailablePinBackend is the safe default. No production backend, bootstrap grant or hardware trust root is implemented.

Protocol: read exact current backend pin; validate old record; stage a nondecreasing next-version policy; reopen the staged record. Preparation does not adopt the pin. Explicit adoption revalidates both records and their one-version transition, reads the backend, refuses conflicts, attempts compare-exchange, and ALWAYS reads back after an attempted write regardless of success/error response. ObservedNext requires the exact proposed pin and a readable matching policy. ObservedPrevious means old state was observed; Conflict means a different or missing state/record; Unknown means readback unavailable. No outcome authorizes execution or attributes the write to a particular actor. No automatic retry, fallback, cleanup or pin bootstrap.

Interruption model: stop before compare-exchange leaves old pin current and new file staged; successful durable pin change means fresh readers must read the new exact record; lost response is resolved by readback, otherwise Unknown. An independently advanced pin with a missing file fails closed, never falls back. If staging leaves a partial file, ORCH-057 prevents replacement; separate inspection remains necessary. Preparation failure can leave staged evidence. No cross-device atomic file+backend transaction is claimed.

Eight tests exercise unavailable backend, staged-but-not-adopted state, successful/idempotent observation, three ambiguous write/readback cases, competing pin, missing staged file, missing current file and absent bootstrap pin. FixtureBackend is VOLATILE fault injection only, deliberately not a production-conforming backend. These are protocol fault scenarios, not actual independent-device restart/power-loss tests. ORCH-055/057 process tests remain in regression coverage.

AI-review through three lenses: TRIAS — explicit backend boundary and unavailable default preserve authorization/activation gates; ORACLE — readback handles ambiguous responses but cannot prove a dishonest/stale backend's properties, with real hardware/backend validation NOT EXECUTED; MENTOR — named outcomes and preserved records make operator recovery auditable. Dissent: production anti-rollback remains HOLD pending a provisioned independent backend, its authorization lifecycle and actual durability/rollback tests.

Next transition: choose and provision a concrete independent local trust root (for example a reviewed TPM/secure-element-backed implementation), implement this contract and validate access, concurrency, restart and rollback on that platform. A network-only backend would limit offline availability. Existing human independent review and GO-13 gates apply before merge or activation. CI evidence is recorded against exact head/base in the PR.
