# ORCH-057 — Pinned policy record storage

DERIVED review-only implementation on ORCH-056. The new create-only policy store persists registry identity, pinned public key and both minimum floors. It syncs file and directory and returns a proposed pin; staging never adopts policy. Reads require an independent exact PolicyPin, do not scan for latest and never fall back to an older record. verify_with_pinned_policy reopens and verifies policy before checking the signed anchor.

PLPOL001 frame: 8-byte magic, big-endian u64 version, 32-byte registry ID, 32-byte public key, big-endian u64 minimum revision and epoch, then 32-byte SHA-256 commitment (128 bytes total). Commitment hashes domain PALACO-ORCH-057-POLICY-RECORD-v1 followed by the version and policy fields in that order. It is a checksum/independent-pin comparison, not a signature.

stage_policy_advance requires the previous record to match its supplied pin, forbids lower floors and registry/key changes, uses checked version increment, and creates the next immutable record. No key rotation or pin adoption is implied. Concurrent proposals cannot overwrite the same version. Partial files block reuse and remain for inspection.

Eight runnable tests cover exact reopen/missing pin, no overwrite, declining floors and identity/key changes, valid-checksum rollback against a current independent pin, missing-current no fallback, partial/oversized data, signed receipt rejection under advanced floors, Unix symlink denial, and advanced policy reopen in a fresh process. One ignored helper is explicitly spawned by the restart test. Tests demonstrate that replaying the pin too defeats the comparison.

Threat boundary: current pins must be authenticated and retained outside the rollback domain of these policy files. This PR does NOT implement TPM/secure-element counters, an authenticated external pin service, or the atomic policy-record/pin adoption protocol. Local filesystem cannot by itself prove that its own entire history was not restored. Caller-owned directory/ancestors and no hostile concurrent writers are required; metadata/open TOCTOU and physical power-loss durability remain unresolved. Existing lower-level verifier APIs remain available; the new review path is not global enforcement.

AI-review through three lenses: TRIAS — staging/proposed pins do not grant adoption or execution authority; ORACLE — tests establish comparison relative to an independent pin, not authenticity or monotonic persistence of that pin; MENTOR — exact-version reads and explicit missing-pin failure avoid silent fallback while preserving diagnostic evidence. Dissent: production anti-rollback remains HOLD until an independent monotonic pin backend and crash-safe adoption protocol are supplied and reviewed.

Next engineering transition: specify and test the atomic adoption protocol through an explicit independent monotonic pin backend contract, including absent backend, conflict and interrupted adoption. A production backend requires an identified hardware/service trust root; none is claimed here. Human independent review and existing GO-13 gates remain for merge/activation. Exact-head CI evidence is recorded in the PR.
